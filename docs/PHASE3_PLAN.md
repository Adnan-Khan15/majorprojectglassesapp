### Things in the prompt I think are wrong or need a tweak

1. **ToF sampling time.** 5–7 samples × 200 ms timing budget is **1.0–1.4 s**. Done before the image (as today), that adds about 1 s to every tap. Instead, the board starts ToF sampling at capture time **on a separate task, in parallel with the image transfer** (about 2 s today), and sends the ToF result as its own message after the image, tagged with the image id. The phone doesn't need the distance until it composes the sentence, so OCR and Gemma start as soon as the image is in. This is why the distance moves out of the CONTROL header in v2.
2. **GPIO21 is shared.** On the Sense board, GPIO21 is the user LED **and** the microSD chip-select. That's fine because we never mount the SD card, but it's a second reason the SD card can't be used. The XIAO user LED is wired **active-LOW** per Seeed's docs. The firmware treats it that way, and the hardware test checks it.
3. **MAX98357A mono mix.** If the firmware sends the **same sample on both I2S channels**, the SD-pin mode (left, right, or (L+R)/2) no longer matters for what you hear. That takes question 1 off the critical path. GAIN still decides the loudness ceiling, so I start at a conservative 50% software ceiling.
4. **Offline claim.** ML Kit's Google Play services dependencies normally **merge `INTERNET` and `ACCESS_NETWORK_STATE` into the manifest** even if we never declare them. The `offline` flavor must strip them explicitly with `tools:node="remove"`, and the permission-check script has to look at the *built APK*, not our manifest.
5. **Flavors in M1, not M8.** The in-app download (M1) needs `INTERNET`. Adding it to `main` and taking it out again in M8 is churn, so the `offline` / `withDownload` flavors come in M1. The permission-check script and release hygiene stay in M8.
6. **Tap is detected on release.** Telling tap from hold means waiting for the release (or 500 ms). Today a capture starts on press, so a tap now starts up to about 0.5 s later (in practice, however long the finger is down). For a tap, the photo is taken at release.
7. **Golden ADPCM vectors.** Vectors generated by one of the two implementations only prove they agree with each other. They come from an independent Python reference (`scripts/gen_adpcm_vectors.py`), and both the C++ and Kotlin tests check against those committed vectors.

## 2. Milestones

### M0: Baseline, transfer diagnostics, instrumentation
I can't rerun the v0.3.1 hardware retest. What I can do is make the next run tell us *why* if it fails again.
- Firmware: log and send per-capture diagnostics: frame index since boot, ms since camera init, JPEG size, sensor AEC/AGC values, and the ToF raw status. Log `esp_reset_reason()` at boot (to catch brownouts). If a frame is under 8 KB, grab one more and log both sizes. That's a mitigation that's visible in logs, not a fix for an unknown cause.
- Phone: `InteractionLog`: per interaction, stage timestamps go to a CSV row, plus `scripts/latency_report.py` (p50/p90 per stage).
- `CLAUDE.md`.
- Tests: CSV row formatting, latency report script on a sample CSV.

### M1: Model delivery (no model in the APK)
- Delete `ModelInstaller.kt`, the asset-part `noCompress` block, the splitting in `scripts/fetch-model.sh`, and the README's two-part APK steps.
- `ai/ModelStore.kt`: manifest-driven (`assets/model-manifest.json`), states `Missing / Importing(p) / Verifying(p) / Ready(version,size,sha256) / Corrupt(reason)`. Three sources: SAF import (`ACTION_OPEN_DOCUMENT`, copy with progress + space check), developer drop-in at `getExternalFilesDir("models")` used in place, and an optional resumable HTTP Range download (`withDownload` flavor only, Wi-Fi only by default). The SHA-256 result is cached against (path, size, mtime), so a 2.6 GB file isn't re-hashed on every launch.
- Flavors `offline` (no network permission at all) and `withDownload`.
- `scripts/fetch-model.sh` becomes a developer helper: download + verify + `adb push` to the drop-in folder.
- Tests: the ModelStore state machine against a fake filesystem (missing, partial, corrupt, ready, drop-in, cache invalidation).

### M2: Firmware hardware bring-up
- Restructure `src/`: `pins.h`, `camera`, `tof` (VL53L0X), `speaker` (I2S1 TX), `mic` (I2S0 PDM RX), `console`, `ble_link`, `main` (state machine). Pure logic (ADPCM, CRC32, framing, median filter) goes in `lib/glasses_core/` so the `native` test env can build it.
- Pins: button GPIO1; LED GPIO21 (active-LOW); I2S BCLK GPIO5, WS GPIO6, DOUT GPIO4; PDM CLK GPIO42, DATA GPIO41; ToF SDA GPIO9, SCL GPIO7. Pull-downs only on D1, D2, D6.
- Serial console: `help`, `caps`, `tone [hz] [ms]`, `mic [s]`, `tof [n]`, `vol <0-100>`, `p` (tap), `h` (simulated hold, records 2 s).
- ToF: `pololu/VL53L0X`, 200 ms budget, N samples (default 5), drop timeouts and out-of-range (≥ 8190 mm), report median / count / spread / flags.
- Tests (native): median + spread + flags, CRC32 against known vectors.

### M3: BLE protocol v2 + throughput spike
- New characteristics (same UUID pattern): `…0005` COMMAND (write), `…0006` EVENT (notify), `…0007` AUDIO_UP (notify), `…0008` AUDIO_DOWN (write without response). CONTROL / IMAGE_DATA / RESULT_TEXT keep working.
- CONTROL header v2: `{ver=2, image_id u16, size u32, crc32 u32, w u16, h u16, diag…}`. The phone also still accepts the 6-byte v1 header.
- Image chunks stay as 244 B indications (no change without data). Add CRC check, abort, and resend (the board keeps the last JPEG in PSRAM).
- Capabilities handshake: protocol version, firmware version, feature bits, audio parameters, reset reason.
- Throughput spike: COMMAND `THROUGHPUT_UP n` makes the board send *n* bytes as AUDIO_UP notifications with sequence numbers. The phone writes *n* bytes to AUDIO_DOWN, and the board reports bytes / frames / gaps over EVENT. Diagnostics shows KB/s and loss for both directions. PHY 2M is a toggle for the test, off by default.
- Tests: all framing codecs (Kotlin), plus the same frame layouts in C++ (native).

### M4: Speaker path
- Phone: `TextToSpeech.synthesizeToFile` → WAV parse → resample to 16 kHz mono → IMA ADPCM frames (400 samples per frame, 8 B header) → AUDIO_DOWN, gated by credits.
- Board: decode into a PSRAM PCM ring (2 s), pre-buffer 400 ms (or start at end-of-stream), fade in, play on I2S1 at 16 kHz with the sample duplicated on L+R. Software volume ceiling, default and max 50% of full scale. Volume is set from the app and stored in NVS. On underrun, play silence and send an event. Send PLAY_STARTED / PLAY_DONE.
- `speech/SpeechOutput`: Speak on glasses / phone / both, falling back to the phone if the glasses aren't connected or lack a speaker. Replaces `ResultAnnouncer`.
- Tests: golden ADPCM vectors (Kotlin + C++ native), resampler, WAV parser, credit flow logic.

### M5: Voice pipeline on the phone only
- `voice/SpeechToText` interface. **Spike A** `GemmaAudioStt`: audio + image + text in one Gemma call that returns JSON with `heard`. **Spike B** `AndroidOnDeviceStt`: `SpeechRecognizer.createOnDeviceSpeechRecognizer` fed from a file via `EXTRA_AUDIO_SOURCE` (API 33+).
- The STT spike harness in Diagnostics runs every WAV in a folder through each engine and exports CSV. `scripts/wer.py` scores it against your reference transcripts. Results go in `docs/STT_SPIKE.md` (template; you record the clips).
- `ai/AnswerComposer`: the JSON contract, validation, retry once on a parse failure, safety wording, the ToF/center rule, rounding, and units.
- "Ask with phone mic": phone mic, then the latest glasses photo or a gallery photo, then the answer on the phone speaker.
- Tests: JSON parse and retry, composer rules (all of section 5 of the prompt), WER script.

### M6: Hold-to-talk on the glasses
- Firmware state machine: IDLE → (press) PRESSED → tap: CAPTURE_SEND · hold: EARCON → RECORDING (cap 10 s) → (release) CAPTURE_SEND + thinking earcon → WAIT_ANSWER → PLAYING. Barge-in from PLAYING or WAIT_ANSWER. Never record while playing.
- AUDIO_UP stream with sequence numbers. The phone fills gaps with silence and logs loss.
- Spoken failures for every error path.

### M7: App UI
Setup wizard, Home (status chips, Describe, Ask with phone mic, result card with Replay / Stop), History (JSON + thumbnails in app storage, detail view, export CSV/JSON, delete), Settings, Diagnostics (BLE log, ToF live + calibration walk-through, tone, mic meter with record/playback, throughput test, latency log export, STT spike). Material 3 light/dark, 48 dp targets, TalkBack labels, haptics, spoken state changes.

### M8: Diagnostics, test protocol, release hygiene
`scripts/check-apk-permissions.sh`, `docs/HARDWARE_TESTS.md`, `docs/TOF_TEST_PROTOCOL.md`, a README rewrite, and `CLAUDE.md` kept current.

## 3. Risks

| Risk | Effect | Mitigation |
|---|---|---|
| Gemma audio quality on Indian English or in noise is unknown | Wrong questions answered | The spike decides; `SpeechToText` interface; Spike B as fallback |
| Gemma with audio + image in one call may be slower than 9 s, or GPU audio may be unsupported | Latency | `audioBackend` = CPU if GPU fails; measure in the spike |
| BLE notification loss for AUDIO_UP | Dropped words | Sequence numbers + silence fill + loss %; the throughput spike sizes it |
| Downlink audio throughput with write-without-response unknown on your phone | Stutter | Credits + 400 ms pre-buffer; the spike measures |
| Speaker current spikes → brownout (camera + radio + amp on USB / battery) | Resets mid-answer | Volume ceiling, fade-in, reset-reason logged and shown in the app, 100 µF cap recommended |
| PDM mic level and DC offset unknown | Quiet or clipped audio | DC-blocking filter + software gain, set from the `mic` console meter |
| `synthesizeToFile` voice and sample rate vary by phone and engine | Resampler input differs | Read the rate from the WAV header and resample generically |
| VL53L0X narrow cone vs. camera field of view | Wrong distance for off-centre things | Centre-only rule + calibration of the centre region |
| `platform = espressif32` unpinned → a future core 3.x breaks the legacy I2S code | Build break | Pin the platform version |
| ML Kit adds network permissions | The offline claim is false | Remove in the flavor manifest + script check on the APK |
